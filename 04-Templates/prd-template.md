# PRD 文档模板

> 本模板供 ProductManager 使用，输出标准 PRD 文档。
> 示例场景基于安伴 Guardian 智慧养老平台实际功能。

```
---
> **作者**：ProductManager
> **日期**：[YYYY-MM-DD]
> **版本**：v1.0
> **状态**：草稿
> **关联**：[上游：CEO 决策] [下游：SmartCareExpert、UIDesigner]
---

## PRD：[功能名称]

### 1. 需求背景
[为什么做这个功能？当前存在什么问题？]

示例（跌倒告警推送）：
> 当前老人跌倒后只能在 Web 管理端看到告警，家属无法实时获知。
> 需要在跌倒事件发生时，通过微信小程序推送告警给家属，减少响应延迟。

示例（家属绑定码流程）：
> 家属首次使用小程序时需绑定老人。当前流程需要管理员手动操作，
> 需要让家属在小程序端自行输入绑定码完成绑定。

### 2. 用户故事

| 角色 | 用户故事 | 优先级 |
|------|----------|--------|
| 家属 | 作为家属，我希望在老人跌倒时第一时间收到小程序告警通知，以便及时联系护理员/拨打急救 | P0 |
| 护理员 | 作为护理员，我希望告警生成后系统自动通知我（钉钉/企微），不需要时刻盯着屏幕 | P0 |
| 管理员 | 作为管理员，我希望能为一键为老人生成绑定码，家属扫码或输入后即可绑定 | P1 |
| 老人 | 作为老人，我希望设备自动监测我的状态，发生异常时自动通知家属 | P0 |

### 3. 功能描述

#### 3.1 核心流程

示例（老人跌倒告警推送）：
1. 毫米波雷达检测到跌倒 → MQTT 上报 raw 数据
2. radar-collector 接收 → POST /api/v1/radar/data 转发到后端
3. 后端 process_radar_data() 判断 fall_status=1 → 检查告警规则
4. 去重窗口内未推过 → 创建 t_alert_record（alert_type=fall, severity=emergency）
5. 根据告警规则 notify_channels → 钉钉/企微/短信/微信订阅消息
6. 小程序 10s 轮询 → 拉取到新告警 → 显示在告警列表
7. 管理员在 Web 端处理告警 → handled_status 更新为 2

示例（家属绑定码流程）：
1. 管理员在 Web 端为老人点击"生成绑定码" → POST /api/v1/family/bind-codes/generate
2. 后端生成 6 位随机码（24小时过期）→ 存入 t_bind_code
3. 管理员将绑定码告知家属（线下/电话/打印）
4. 家属打开小程序 → 进入绑定页 → 输入 6 位码
5. POST /api/v1/family/bind → 校验码有效性 → 创建 t_family_elderly 绑定关系
6. 标记绑定码 is_used=1 → 家属首页刷新显示已绑定老人

#### 3.2 异常流程

示例：
- **绑定码错误**：提示"绑定码无效或已过期"，允许重新输入（不限次）
- **重复绑定**：提示"您已绑定过该老人"，不重复创建关系
- **雷达断线**：超过 30 分钟无数据 → Zabbix Trigger 触发 → 设备离线告警
- **API 超时**：radar-collector 重试 3 次后丢弃本条数据，记录错误日志

#### 3.3 边界条件
- **告警去重**：同一老人同一类型的告警 5 分钟内不重复生成（ALERT_DEDUP_WINDOW）
- **绑定码过期**：生成后 24 小时未使用自动失效
- **并发**：同一老人同时触发多个告警规则时，各规则独立生成告警记录
- **权限**：家属只能看到已绑定老人的数据；护理员只能看到分配老人的数据

### 4. 交互说明

示例（小程序告警详情页）：
- **入口**：底部 Tab "告警" → 告警列表 → 点击某条告警
- **展示**：告警类型标签（跌倒红色）、发生时间、处理状态、关联老人信息
- **反馈**：告警列表 10s 自动刷新；未处理告警显示红点 badge

示例（Web 绑定码管理）：
- **入口**：左侧菜单"家属绑定" → "生成绑定码"按钮
- **操作**：选择老人 → 选择关系（子女/配偶/亲属）→ 点击生成
- **反馈**：弹出结果窗显示 6 位绑定码 + 二维码 + 到期时间，支持复制/分享

### 5. 数据需求

| 数据 | 来源 | 说明 |
|------|------|------|
| 雷达原始数据 | MQTT Topic `smartcare/{inst}/+/radar/data` | 包含 fall_status, heart_rate, breath_rate, in_bed 等 |
| 告警规则 | t_alert_rule 表 | 配置阈值 JSON、严重级别、通知渠道 |
| 家属信息 | t_family 表 | openid/unionid 驱动的家属账号 |
| 绑定码 | t_bind_code 表 | 6 位随机码 + 过期时间 + 关联老人 |
| 设备在线状态 | t_radar_device.online_status | 由数据上报自动更新 |

### 6. 埋点需求
- 绑定码生成次数（按老人/管理员统计）
- 绑定成功率（已使用 / 总生成数）
- 跌倒告警推送到达率（微信订阅消息成功率）
- 告警处理时效（从创建到 handled 的时间间隔）

### 7. 验收标准

示例（跌倒告警推送）：
- [ ] 雷达上报跌倒数据后 3 秒内后端生成告警记录
- [ ] 告警生成后 5 秒内钉钉/企微消息送达
- [ ] 小程序轮询间隔内（10s）家属可见新告警
- [ ] 同一老人 5 分钟内重复跌倒不产生多条告警
- [ ] 告警处理状态流转: 未处理(0) → 处理中(1) → 已处理(2)

示例（家属绑定码）：
- [ ] 管理员选择老人后可一键生成 6 位绑定码
- [ ] 绑定码 24 小时后自动失效，使用时提示"已过期"
- [ ] 家属输入正确绑定码后，首页立即显示绑定老人卡片
- [ ] 同一家属重复输入相同绑定码提示"已绑定"
- [ ] 一个绑定码被使用后无法被其他家属再次使用

### 8. 运营指标

| 指标 | 目标值 |
|------|--------|
| 跌倒告警推送到达率 | ≥ 95% |
| 告警平均响应时间（创建→处理） | ≤ 60 秒 |
| 家属绑定成功率 | ≥ 90% |
| 设备在线率 | ≥ 99% |
```
