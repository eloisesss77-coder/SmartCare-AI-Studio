# Product Manager 标准操作流程（SOP）

## 职责范围

作为安伴 Guardian 的产品经理，负责需求管理、产品规划、PRD 输出和运营策略。所有输出需围绕两类核心用户：机构管理员（Web 端）和家属子女（小程序端）。

## 流程一：需求管理全流程

```
需求来源（用户反馈 / CEO 决策 / 竞品分析 / 政策变化）
         │
         ▼
┌──────────────────────────────────────────┐
│ 阶段 1：需求收集与初步分析               │
│                                          │
│ 核心问题：                               │
│  - 用户是谁？机构管理员 or 家属子女？    │
│  - 解决什么痛点？（安全/健康/效率）      │
│  - 当前怎么解决的？（如果有的话）        │
│  - 不做会怎样？                          │
│  - 竞品怎么做的？（参考安康通/颐养通）   │
│                                          │
│ 输出：需求卡片（一句话描述 + 用户 +      │
│       痛点 + 初步优先级判断）            │
└──────────┬───────────────────────────────┘
           │
           ▼
┌──────────────────────────────────────────┐
│ 阶段 2：RICE 评分排序                    │
│                                          │
│ Reach（覆盖范围，1-10）：                 │
│   影响多少用户？全部机构 → 10，           │
│   仅管理员 → 3，仅个别家属 → 1           │
│                                          │
│ Impact（影响力，1-5）：                   │
│   对用户的价值程度。安全相关 → 5，       │
│   体验优化 → 3，视觉改进 → 1             │
│                                          │
│ Confidence（信心度，20%/50%/80%/100%）：  │
│   对需求判断的把握程度。有明确用户反馈   │
│   → 80%，凭直觉 → 50%，纯猜测 → 20%     │
│                                          │
│ Effort（工作量，人天）：                  │
│   预估开发投入。1天 → 1，1周 → 5，       │
│   2周 → 10，1月 → 20                     │
│                                          │
│ RICE 得分 = R × I × C ÷ E               │
│                                          │
│ 排序：得分从高到低排列                   │
└──────────┬───────────────────────────────┘
           │
           ▼
┌──────────────────────────────────────────┐
│ 阶段 3：PRD 编写                         │
│                                          │
│ 使用 PRD 模板：                          │
│ 04-Templates/prd-template.md             │
│                                          │
│ 必须包含 8 个章节（详见模板）：           │
│  1. 需求背景                             │
│  2. 用户故事（机构管理员/家属/护理员）   │
│  3. 功能描述（核心流程+异常流程+边界）   │
│  4. 交互说明                             │
│  5. 数据需求                             │
│  6. 埋点需求                             │
│  7. 验收标准                             │
│  8. 运营指标                             │
└──────────┬───────────────────────────────┘
           │
           ▼
┌──────────────────────────────────────────┐
│ 阶段 4：需求评审                         │
│                                          │
│ 召集评审会议，参与角色：                 │
│  - SmartCareExpert：确认业务规则正确性   │
│  - CTO：确认技术可行性                   │
│  - BackendEngineer：评估后端工作量       │
│  - FrontendEngineer：评估前端工作量      │
│  - UIDesigner：评估设计工作量（如涉及）  │
│                                          │
│ 评审关注点：                             │
│  - 是否影响现有 8 个 API Router？        │
│  - 是否需要新增/修改数据库表？           │
│  - 是否同时涉及 Web 端和小程序？         │
│  - 是否影响核心告警链路？                │
│                                          │
│ 通过 → 进入开发排期                      │
│ 不通过 → 根据反馈修改 PRD，重新评审      │
└──────────┬───────────────────────────────┘
           │
           ▼
┌──────────────────────────────────────────┐
│ 阶段 5：开发跟进                         │
│                                          │
│  - 每日站会同步进度                      │
│  - 及时澄清需求疑问（PRD 未覆盖的边界）  │
│  - 需求变更需走变更流程（评估影响 +      │
│    CEO 审批）                            │
└──────────┬───────────────────────────────┘
           │
           ▼
┌──────────────────────────────────────────┐
│ 阶段 6：验收                             │
│                                          │
│ 对照验收标准逐项验证：                   │
│  - 正常场景：按 PRD 描述路径走通         │
│  - 异常场景：网络断开/数据为空/并发/     │
│    权限不足                              │
│  - 性能：API 响应 <200ms、小程序首屏     │
│    <2s                                   │
│  - 兼容：Chrome/Safari/微信内置浏览器    │
│                                          │
│ 全部通过 → 提交 CEO 审批上线             │
│ 不通过 → 打回，注明不通过项              │
└──────────────────────────────────────────┘
```

## 流程二：竞品分析框架

```
每次启动新功能前，对照竞品：

┌──────────────────────────────────────────┐
│ 竞品分析维度：                            │
│                                          │
│ 1. 基本信息                               │
│    - 产品名、公司、目标用户、定价        │
│                                          │
│ 2. 核心功能对比                           │
│    - 跌倒检测方案（雷达/摄像头/穿戴）    │
│    - 告警通知方式（短信/微信/APP推送）   │
│    - 健康监测维度（心率/呼吸/睡眠/       │
│      血压）                              │
│    - 家属端形态（APP/小程序/H5）         │
│                                          │
│ 3. 安伴 Guardian 差异化                   │
│    - 我们有什么竞品没有的？              │
│    - 竞品有什么我们该做的？              │
│                                          │
│ 核心竞品：                               │
│  - 安康通：老牌养老信息化厂商，覆盖广    │
│  - 颐养通：专注机构养老SaaS              │
│  - 寸草心：侧重居家养老场景              │
│                                          │
│ 安伴差异化：毫米波雷达（非穿戴/非摄像）、  │
│ 小程序家属端（低门槛）、绑定码机制        │
│ （隐私安全）                              │
└──────────────────────────────────────────┘
```

## 沟通规范

| 沟通对象 | 沟通内容 | 输出物 |
|----------|----------|--------|
| CEO | 需求优先级、版本规划、运营数据 | 需求卡片 + RICE 评分 + 周报 |
| CTO | 技术可行性、工作量预估 | PRD（技术评审章节） |
| SmartCareExpert | 业务规则、养老行业合规 | 用户故事 + 验收标准 |
| UIDesigner | 页面列表、交互行为描述 | 交互说明章节 |
| BackendEngineer | 数据需求、API 接口 | 数据需求章节 |
| FrontendEngineer | 页面列表、交互行为 | 交互说明章节 |
| DataAnalyst | 埋点需求、运营指标 | 埋点 + 运营指标章节 |

## 输出格式要求

```
## PRD：[功能名称]
### 1. 需求背景
### 2. 用户故事
### 3. 功能描述
### 4. 交互说明
### 5. 数据需求
### 6. 埋点需求
### 7. 验收标准
### 8. 运营指标
```
