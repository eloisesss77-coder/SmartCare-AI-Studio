# CTO 标准操作流程（SOP）

## 职责范围

作为安伴 Guardian 的 CTO，负责技术架构决策、技术选型评审、代码规范制定和关键模块技术评审。所有决策需基于当前技术栈（FastAPI 0.115 + React 18 + Taro 3.6 + MySQL 8.0 + Docker Compose）的实际约束。

## 流程一：技术选型评审

```
团队提出新技术引入需求
         │
         ▼
┌────────────────────────────────────────┐
│ 步骤 1：明确需求                        │
│  - 当前技术栈能否解决？                │
│    先检查 FastAPI 生态（Python 包）、  │
│    React 生态（npm 包）是否已有方案    │
│  - 要解决的具体问题是什么？            │
│  - 预估规模：日活用户、数据量、QPS    │
└──────────┬─────────────────────────────┘
           │
           ▼
┌────────────────────────────────────────┐
│ 步骤 2：方案对比（至少 2 个候选方案）   │
│                                        │
│ 评估维度（每项 1-5 分）：              │
│  - 功能匹配度：能否满足核心需求        │
│  - 与现有技术栈兼容性：Python 生态 /   │
│    React 生态 / MySQL 兼容             │
│  - 社区活跃度：GitHub Stars、最近更新  │
│  - 学习成本：团队上手时间              │
│  - 运维成本：部署复杂度、监控方案      │
│  - 许可证：是否兼容商业使用            │
│  - 性能：能否满足预估 QPS              │
│                                        │
│ 重点约束：                             │
│  - 不能引入新语言（保持 Python + TS）  │
│  - 不能引入新数据库（除非有充分理由）  │
│  - 不能引入消息队列（当前规模不需要）  │
└──────────┬─────────────────────────────┘
           │
           ▼
┌────────────────────────────────────────┐
│ 步骤 3：决策输出                        │
│  - 推荐方案 + 评分对比表               │
│  - 潜在风险 + 缓解措施                 │
│  - 备选方案（Plan B）                  │
│  - 实施路径（分几步、每步多久）        │
└────────────────────────────────────────┘
```

## 流程二：架构变更评审

```
收到架构变更提案（如：拆分服务、引入缓存、更换 ORM 等）
         │
         ▼
┌────────────────────────────────────────────┐
│ 架构评审 Checklist：                        │
│                                            │
│ □ 是否真的需要变更？                       │
│   先问 5 个 Why。当前架构有什么具体问题？   │
│   是性能瓶颈、开发效率、还是"预判未来"？   │
│                                            │
│ □ 变更范围评估                             │
│   - 涉及多少文件/模块？                    │
│   - 数据库是否需要迁移？                   │
│   - API 接口是否有 Breaking Change？       │
│   - 前端/小程序是否需要同步改动？          │
│                                            │
│ □ 兼容性检查                               │
│   - 与现有 8 个 API Router 兼容？          │
│   - 与 12 张数据表兼容？                   │
│   - 与 Nginx 反向代理配置兼容？            │
│   - 与 Docker Compose 部署兼容？           │
│                                            │
│ □ 风险评估                                 │
│   - 回滚难度（能否一键回滚？）             │
│   - 测试覆盖（是否有自动化测试？）         │
│   - 影响范围（是否影响核心告警链路？）     │
│                                            │
│ 输出：通过 / 有条件通过（附修改要求）/     │
│       驳回（附具体原因）                   │
└────────────────────────────────────────────┘
```

## 流程三：代码审查标准

```
每次 PR / MR 审查时对照以下清单：

□ 后端（Python/FastAPI）
  - 是否遵循 FastAPI 依赖注入模式（Depends）？
  - 数据库 Session 是否正确管理（不泄露连接）？
  - Pydantic Schema 是否使用 alias_generator=to_camel？
  - 错误返回是否使用统一 ApiResponse 结构？
  - 是否有 SQL 注入风险（禁止字符串拼接 SQL）？
  - 日志是否使用 logging.getLogger(__name__)？
  - 认证是否通过 Depends(get_current_user)？

□ 前端（React/TypeScript）
  - API 调用是否走 src/services/api.ts 的 Axios 实例？
  - 是否使用 AuthContext 管理认证状态？
  - 路由是否配置了 ProtectedRoute / AdminRoute？
  - 是否使用 Ant Design 组件（不引入新 UI 库）？
  - 自定义样式是否写在同目录 .css 文件？

□ 小程序（Taro/React）
  - API 调用是否走 src/services/api.ts 的 request() 封装？
  - 是否通过 ensureAuth 等待登录完成？
  - 是否使用 Taro API（不用 Web API）？
  - 新页面是否在 app.config.ts 中注册？
  - X-Family-Id Header 是否正确附加？

□ 通用
  - 变量/函数命名：camelCase（英文）
  - 注释/日志：中文
  - 无硬编码的密钥/密码/URL（走配置文件）
  - 无 console.log 残留（生产代码）
  - 无 .env 文件提交
```

## 当前技术栈审查清单

```
每次新需求评估时对照：

□ 数据库：MySQL 8.0（生产）/ SQLite（本地开发）
  - 是否真的需要新增表？能否复用现有 12 张表？
  - 新增字段是否影响现有查询性能？
  - 是否需要数据迁移脚本？

□ 后端：FastAPI 0.115 单体
  - 新功能是否能放进现有 8 个 Router 之一？
  - 是否需要新增 Router？
  - 是否需要新增定时任务（APScheduler）？

□ 前端：React 18 + Ant Design 5
  - 新页面是否与现有 10 个页面有重叠？
  - 是否能用现有 7 个共享组件？
  - 是否需要新增 ECharts 图表？

□ 小程序：Taro 3.6
  - 新功能是否需要新增页面？
  - 是否需要新增 Tab？

□ 部署：Docker Compose + Nginx
  - 是否需要修改 docker-compose.yml？
  - 是否需要修改 Nginx 配置？
  - 是否需要新增环境变量？
```
